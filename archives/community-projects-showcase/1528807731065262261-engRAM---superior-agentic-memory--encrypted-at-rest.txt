    engRAM is agentic vector memory that stores greater context more efficiently than other memory backends: decisions bound to their questions, importance-weighted hybrid recall, and AEAD on every byte at rest - including the embedding vectors. 100% offline, 100% portable, 100% encrypted. 
    
    Cross platform - one vector memory file can be used by Hermes, Claude, OpenClaw, and other agents all at once. 
    
    Memory behavior
    • Short answers are not discarded - "OK" is stored with the question it answered, so you don't need to repeat yourself or remember how to do the same task twice. 
    • Deterministic importance ranks recall (consent/decisions and personal/machine context above noise)
    • Hybrid search (vector + keyword), exact SIMD top-k (recall 1.0 by construction)
    • Pinned embedding model (SHA-256 enforced) so cosine space does not silently rot
    • No LLM inside the memory layer - capture/rank/encrypt are deterministic and reproducible
    
    Security / offline
    • Vectors encrypted at rest (most memory stacks leave them plaintext)
    • Crypto-shred forget: destroy the per-record key, content is gone
    • Fully offline: bundled ONNX embedder, runtime aborts on any network attempt
    • Lock/unlock on demand; default unlock stays open until restart or you lock
    • Hash-chained audit, per-caller namespaces, portable single-file vault
    
    Agent wiring
    • Hermes native provider - hermes memory setup, "no setup needed" (no API key/cloud/daemon)
    • Claude + OpenClaw via MCP; CLI for anything else
    • One vault shared across agents and machines (lock → move file → unlock)

    Sorry for the late reply, I never got the notification.
    
    Hermes' native provider (which I take to mean the default memory, not dedicated memory like Hindsight or engRAM) is very basic: similar to a .txt file that stores whatever you explicitly tell the agent to store, like a notes app. The chat/reasoning turn you mention runs through an LLM, so it's almost always cloud unless you're running one locally. engRAM is 100% offline. It never touches the internet, and it actively resists other programs trying to upload its data (weakly, since it's not a firewall, but more resistance than any other memory).
    
    To the crux of your question about using a different model for memory than the main LLM: I think you're conflating vectorization (converting stored memories to vectors, often done with a small local model) with deciding what to store, which is a separate concept. engRAM is, in my biased opinion, the only agentic AI memory that's automatic. Once linked, its instruction set tells Claude (or any agent) what to store and retrieve, with no prompting or toggling needed. It just captures everything relevant.
    
    There's also optional starter memory so you don't begin from scratch: computer and internet "geography" such as machine models and specs, ports, and other facts essential to agentic operations. Our computers and usage patterns aren't that different, so starting from zero memory is, frankly, dumb. Why make the agent learn over time what someone else already learned for you? No need to start like a baby.
    
    Intelligence is the creation of knowledge from other knowledge, all knowledge is actually memory, and people forget the knowledge side of AI because knowledge is treated as "already there," the stuff AI works on. But it's also what AI outputs. A brilliant agent without high-quality memory is like a brilliant human without memory: not very useful.
