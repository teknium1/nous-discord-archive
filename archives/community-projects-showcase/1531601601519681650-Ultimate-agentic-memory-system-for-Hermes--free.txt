    Where Engraphis wins compared to Compartment:
    
    Multi-repo project boundaries: First-class workspace → repo → session scopes, rather than Compartment’s flat namespaces plus caller ACLs. Better for isolating work across repos and sessions.
    
    Time-aware fact history: Record-level valid_at and known_at, plus supersession chains, corrections, promotion, and timelines. Compartment has save/discovery dates and temporal relations, but not equivalent bi-temporal memory recall.
    
    Evolving facts without deletion: Engraphis can add, reinforce, relate, or invalidate a claim while retaining its predecessor for “what changed and why?” queries. Compartment deduplicates near-identical records; correction otherwise relies on deletion or shredding.
    
    Code-native memory: Indexes symbols, calls, imports, files, and code-to-memory links. Supports structural search, dependency paths, git-range impact, and PR graph reports. I found no comparable parser, symbol index, or call graph in Compartment. 
    
    Graph-informed retrieval: Engraphis’s entity and code graph is a normal retrieval arm using PPR, not just a manually queried relation store. Compartment’s ranker is vector plus lexical, while relations are queried separately.

[2026-08-02T21:06:06.696000+00:00] jaixii (id=1533581686770765844)
    Grounded answer contract: Returns a cited answer or explicitly abstains below an evidence threshold. Compartment returns ranked records and warnings, not a citation-bound answer or abstention result.
    
    Prompt-context control: Hard token-budget context packets, compact responses, usage accounting, and adaptive fallback to raw history. Better for agents operating under fixed context windows.
    
    Retrieval and model flexibility: Embedders, vector indexes, rerankers, and optional LLM extraction are interface-driven and swappable. Compartment intentionally pins a bundled embedding space, which improves reproducibility but is less flexible for deployments.
    
    Memory lifecycle tooling: Typed working, episodic, semantic, and procedural memories, plus reinforcement, consolidation, governance, provenance, and inspection. Compartment uses importance and recency ranking and delegates most curation to the host agent.
    
    Engineering-data ingestion: Built-in paths for code, documents, PDF/OCR, audio/video transcription, and PostgreSQL schema ingestion.
    
    Shared-workspace workflows: Optional encrypted workspace sync and hosted team controls, alongside repo and session boundaries. Compartment supports local multi-agent ACLs, but not the same project and team model.

    Alright onto my refutation:
    
    You made 11 separate comparisons claims, not one of them was about memory recall. Zero comparisons of whether the right memory comes back. That's the only thing a memory system does. A feature inventory is not a quality argument.
    
    Workspace/repo/session scopes. Persistent memory is valuable precisely because knowledge crosses boundaries. Scoping by repo reintroduces amnesia at every boundary, and it forces a write time guess nobody can make: when I learn how someone likes their commits written, is that session, repo, or global? Guess narrow and it's invisible later, guess wide and it's a namespace with extra steps. Scoping is what you build when ranking can't separate.
    
    Bi-temporal valid_at/known_at. That's from regulated finance, where you're legally required to reconstruct what was believed on an audit date. Nobody asks an agent what it believed about their printer on July 3rd. You pay that cost on every write and the as-of query never runs. An inferred valid_at that's wrong is worse than none, since it silently reorders truth. What people want here is correction, which is one pointer, not a temporal algebra.
    
    Never deleting, retaining predecessors. You're leading with this, so it's where I'll push hardest. An append only store accumulates known false statements forever and every future query has to outrank them, so the index degrades with every correction. Then the liability half: for memory holding credentials, addresses, medical or legal facts, retaining the predecessor is exactly the thing you must not do. When a password rotates, the old one has to be gone. You framed deletion and shredding as my weakness. Real forgetting is harder to build than never forgetting, and it's the one that survives an erasure request.

[2026-08-04T04:26:40.621000+00:00] maxfreedompollard (id=1534054946553598002)
    Code native memory. Code is the one domain where ground truth is already on disk, free to read, and current, and the agent already has ripgrep and an LSP. A symbol and call index inside a memory system is a stale copy of something authoritative, and a stale call graph is worse than none because it asserts an edge that no longer exists and the agent trusts it over the file. Memory should hold what isn't recoverable from the repo: the decision, why the alternative was rejected, the constraint someone said once. You can't grep those. So yes, no parser in mine. That's a category difference, not a gap.
    
    PPR retrieval. Graph expansion buys recall with precision, surfacing neighbors of hits that are adjacent and often wrong. At personal vault scale the right record is already reachable by vector plus lexical, and the walk adds plausible noise and latency. If the graph is LLM extracted, you pay nondeterminism and extraction error at write time and then let those errors steer retrieval. PPR earns its keep on multi hop questions over large corpora. This isn't that.
    
    Grounded answer with abstention. The agent is the reasoner. Putting a synthesized answer between it and its own evidence stacks a second, smaller model onto the path, and abstention is worse: it's the memory layer deciding the agent doesn't get to see evidence, on a threshold that can't see the conversation. Return ranked evidence, let the model with full context decide. Also llm/client.py speaks OpenAI and Anthropic, so this needs a key and egress. It's the least local first thing on your list.
    
    Token budget packets. If the budget is hard you don't need a fallback, and if you need adaptive fallback to raw history then it isn't hard and the failure mode is the exact thing the budget was for. Separately, 29 MCP tools is 29 schemas in the context window of every request whether they fire or not. That's a permanent context tax levied by the thing meant to save context.

    ## 3. Bi-Temporal valid_at/known_at
    
    **Verdict: Fair hit.**
    
    I over-engineered this in the initial design doc. The current implementation uses a single `recorded_at` timestamp with `observed_at` as optional metadata.     ## 4. Never Deleting, Retaining Predecessors
    
    **Verdict: You misread the implementation. This is where I push back hardest.**
    
    You wrote: *"An append only store accumulates known false statements forever."*
    
    Engram is **not** append-only. Here's what actually happens:
    
    - **Phenotype memories decay** — each has a `decay_rate` (0.05 for semantic/procedural, 0.15 for episodic). Salience drops over time unless reinforced.
    - **Consolidation engine runs on a cron** — it merges related memories, promotes important ones to genome, and *archives* stale ones (sets `memory_tier = 'archived'`, removing them from recall).
    - **Explicit delete endpoints exist** — `DELETE /api/dashboard/memories/:id` physically removes memories.
    - **Supersession** — when a memory is corrected, the old one gets `superseded_at` set, removing it from active recall.
    
    You're right that credentials and rotated passwords must be *gone*, not merely archived. The implementation handles this: genome memories with `sensitivity: high` are flagged for explicit user confirmation before storage, and the delete endpoint performs a hard delete with pgvector index cleanup.
    
    Real forgetting is harder than never forgetting — agreed. That's why Engram has all three mechanisms: decay, consolidation-driven archival, and explicit deletion.

    ## 10. Working/Episodic/Semantic/Procedural Taxonomy
    
    **Verdict: Partially fair — the taxonomy does drive behavior.**
    
    You asked: *"What retrieval behavior actually differs between a semantic memory and a procedural one?"*
    
    The differences:
    
    - **Decay rates differ** — episodic memories decay at 0.15 (faster), procedural/semantic at 0.05 (slower). This means procedural knowledge persists longer by default.
    - **Consolidation priority** — the consolidation engine prioritizes merging procedural memories (workflow patterns) over episodic ones (one-off events).
    - **Recall boosting** — memories matching the user's recent activity sector get a small similarity boost.
    
    You're right that it's partly an enum with a psychology paper attached — the taxonomy could be simpler. But it's not purely decorative; it drives decay and consolidation behavior. Whether the added complexity is worth the marginal improvement in recall quality is a legitimate design question, and I'm open to simplifying it to just `decay_rate: fast | slow` if the sector distinction proves unnecessary in practice.
